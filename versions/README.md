# Versions

upstream OKF의 변화를 추적하고 이 저장소의 원칙·pattern·facet에 미치는 영향을 기록합니다. 그 명세를 해석·적용하는 Mekra Method의 릴리스 기준도 함께 다룹니다.

- [`current.md`](current.md): 현재 권장 기준과 확인한 upstream 기준점
- [`migrations/`](migrations/): 버전 간 실제 전환이 필요한 변경

## 명세와 가이드의 기준

| 기준 | 의미 |
| --- | --- |
| OKF 명세 버전과 확인한 파일 기준점 | 어떤 공식 형식을 해석·적용하는가 |
| Mekra Method 릴리스 태그 | 그 명세 위에서 채택한 운영 지식의 고정된 배포 기준점 |
| 참고한 배포판의 저장소와 커밋 | 대상에 적용할 때 실제로 읽은 가이드의 상태 |

공개판의 `main`은 계속 갱신되는 최신 채택 내용입니다. 릴리스는 비교·재현을 위한 기준점이며, 모든 변경마다 발행하지 않습니다. 대상 번들의 `okf_version`에는 공식 명세 버전을 사용하고 Mekra Method 릴리스 이름을 넣지 않습니다.

## Mekra Method 릴리스

Mekra Method는 OKF Lab과 OKF Method의 지식과 이력을 이어받은 이름이다. 저장소는 `okf-lab`, `okf-lab-kr`, `okf-lab-dev`에서 `okf-method`, `okf-method-kr`, `okf-method-dev`를 거쳐 각각 `mekra-method`, `mekra-method-kr`, `mekra-method-dev`로 개명했다. 기존 `okf-0.2-lab-1` 태그와 그 커밋은 과거 기준점으로 보존하며, 과거 적용 기록의 저장소명과 태그를 새 이름으로 소급해서 바꾸지 않는다.

OKF Method로 전환하며 정한 `method` 태그 규칙과 순번을 유지한다. Mekra 개명 때문에 순번을 다시 시작하지 않는다. 개명 자체는 릴리스를 발행하거나 대상 번들의 OKF 명세 버전을 바꾸지 않는다.

태그는 `okf-<명세 버전>-method-<순번>`으로 이름 짓습니다. 예를 들어 `okf-0.2-method-1`은 OKF 0.2를 권장 기준으로 하는 첫 Mekra Method 릴리스이고, 같은 명세 위의 다음 릴리스는 `okf-0.2-method-2`입니다. 여기의 이름은 규칙을 설명하는 예시이며, 발행 여부는 각 공개판의 실제 태그로 확인합니다.

순번은 해당 명세를 기준으로 한 Mekra Method 릴리스의 순서이며 SemVer 호환성 등급이 아닙니다. 적용 모델, 핵심 해석, 템플릿의 운영 방식이나 주요 사용 흐름이 의미 있게 바뀌면 새 기준점을 검토합니다. 오탈자·표현·링크 수정만으로 새 릴리스를 요구하지 않습니다. upstream 버전이 올라가더라도 영향 검토 후 권장 기준을 전환할 때 새 명세 버전의 `method-1`로 시작합니다.

한국어판 `mekra-method-kr`과 영문판 `mekra-method`는 같은 논리적 릴리스 이름을 사용합니다. 같은 dev 기준에서 공개 범위와 의미를 검토한 두 판의 커밋에 각각 태그를 붙이므로 커밋 해시는 다릅니다. 태그는 발행한 커밋에 고정하고, 이후 수정은 후속 커밋과 필요시 새 릴리스로 남깁니다. 릴리스 설명에는 주요 변화와 적용·전환에 미치는 영향을 각 판의 언어로 기록합니다. 두 판의 확인이 끝나야 공통 릴리스가 완료됩니다. 이 관계의 판단 근거는 [배포 원칙](../okf/distribution.md)에 있습니다.

연구개발 저장소의 모든 커밋에 태그를 붙일 필요는 없습니다. 공개판의 `SYNC.json`이 검토한 dev 기준을 연결하며, 사용자 측의 회고에는 참고한 공개판만으로 당시 가이드를 확인할 수 있어야 합니다.

## 실제 참고 기준을 남길 때

두 릴리스 사이의 `main`을 참고했다면 가까운 태그가 실제 적용 커밋을 대신하지 못합니다. [적용 인계](../APPLICATION.md)에서 실제 읽은 저장소와 커밋을 기존 README나 운영 안내에 짧게 남기면 이후 비교에 도움이 됩니다. 해당하는 릴리스와 명세 기준도 구분해 적을 수 있지만, 별도 `VERSION` 파일이나 모든 개념의 메타데이터로 반복할 필요는 없습니다.

일부 개념만 새 가이드를 참고해 갱신했다면 그 범위를 함께 남겨, 저장소 전체가 같은 기준으로 전환됐다고 오해하지 않게 합니다. 과거 기준이 기록되지 않았다면 이력에서 확인할 수 있는 만큼 찾고 미확인 부분은 그대로 둡니다. [장기 피드백](../FEEDBACK.md)에서는 당시 기준과 현재 가이드의 차이를 관찰한 문제와 연결합니다.

## upstream 변경을 반영하는 흐름

1. 공식 `SPEC.md`의 버전과 diff를 확인합니다.
2. 형식 호환성, 의미 변화, 운영 원칙과 template에 미치는 영향을 나눠 평가합니다.
3. 필요한 문서만 갱신하고 기존 프로젝트의 migration 필요 여부를 기록합니다.
4. 새 프로젝트 권장 버전과 기존 프로젝트의 전환 우선순위를 별도로 판단합니다.

버전 번호만으로 호환성을 단정하지 않습니다. 같은 버전 표기 아래 명세가 바뀔 수 있으므로 확인일과 upstream 파일 기준점을 함께 남깁니다.
